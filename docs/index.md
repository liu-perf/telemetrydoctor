# telemetrydoctor

**telemetrydoctor** 读一份 GPU 监控采样文件（`nvidia-smi` 的三种输出格式都吃），
把它切成阶段，算出**合法的**聚合值，并**拒绝**那些不合法的——而且拒绝时把错误的
倍数一起说出来。因为「这个操作不允许」说服不了任何人，「这么算会小 69 倍」可以。

一条监控 CSV 看起来就是张表格，于是人们对它做表格该做的事：某一列求个均值、取个
最大值、拿速率乘以时长得总量。这三件事都能跑通，都不报错，而在 GPU 监控数据上，
它们都是错的——错出来的还都是看着很合理的数。

## 三个发现

**① `utilization.gpu` 是时间口径，不是强度口径。** 本机一张 RTX 5060 Ti 上实测：

| 负载 | 实际交付 | `utilization.gpu` 报告 |
|---|---|---|
| 64×64 矩阵乘，无间隙连续提交 | **0.046 TFLOPS** | **29.6%** |
| 4096×4096 矩阵乘，四分之一占空比 | **45.4 TFLOPS** | **27.9%** |

**实际算力差 978 倍，仪表盘上差 1.7 个百分点。** 一块写着「29% GPU 利用率」的面板，
对这两个负载显示的是同一个数。它测的是「采样窗口内有没有 kernel 驻留」的时间占比，
对那个 kernel 用了多少硬件完全无感——不是 SM occupancy，也不是 tensor core 活跃度。

同一个实验还掉出第二条：那个 64×64 的负载**主机侧 100% 时间都在提交**，设备侧只报
29.6%。差的 70.4 个点是 launch overhead——真实的设备空转，主机侧计时器看不见。
「我的训练循环一秒都没停」不能证明 GPU 在忙。

**② 采样间隔永远不是名义值。** 一个结尾是 `sleep(1.0)` 的循环不会每秒产出一行。
真实 8 卡节点上每卡读四个 NVML 计数器，循环体本身花掉 0.37 s，文件实际是
**1.376 s/行——比名义值高 37.6%**。同样的测量在单卡上只高 3.0%：**开销随卡数增长，
所以名义值不可能从代码里看出来**，只能从它产出的文件的时间戳里量。

**③ 固定的「忙」阈值扛不过换负载。** 同一批 8 卡机器上三个真实负载的 SM 平台值是
**48.4% / 69.9% / 94.1%**（检测训练 / 推理 decode / 分割训练）。`sm >= 90` 在其中
两个上一行都选不出来。所以阈值按文件现算（Otsu 法，零依赖零参数），而且——更重要
的——数据支撑不了的时候**拒绝给**。

## 诚实性设计：aggregation contract

这是同一套诚实性装置的第三代。regressiondoctor 给每条判定挂 `noise_basis`，
fitdoctor 给每个数字挂 `basis`——两者回答的都是「这个数从哪来」。这一个回答的是
**「这个数我能拿去做什么运算」**：

| 判定 | 含义 |
|---|---|
| `ok` | 这个运算是成立的 |
| `within_phase` | 只在单个阶段内成立；跨越加载+空闲+工作的均值哪个都不描述 |
| `meaningless` | 能算出一个数，但那个数不回答任何问题 |
| `forbidden` | 会给出错误答案，而且错的倍数是已知的 |

`power_w` 是这张表的对照组：它是瞬时读数，所以 `均值 × 时长` 真的是焦耳——监控文件
里唯一一个成立的积分。没有它，这张表就只是一串禁令，没法证伪。

## 跑起来长什么样

全部命令跑在提交进仓库的合成 fixture 上，不需要 GPU、不需要联网。

论点集中在**状态标签**上：这个工具在它没有把握的地方拒绝给出一个数。

## 七部曲里的第六部

七个项目的关键数字汇总在一页上：[**Dashboard**](https://liu-perf.github.io/nodebench/dashboard.html)。

- 第一部 [nodebench](https://github.com/liu-perf/nodebench)：测量。
- 第二部 [benchdoctor](https://github.com/liu-perf/benchdoctor)：把测量时踩过的坑变成静态检查规则。
- 第三部 [tracedoctor](https://github.com/liu-perf/tracedoctor)：把 benchdoctor 自己承认看不见的边界变成动态 trace 检查规则。
- 第四部 [regressiondoctor](https://github.com/liu-perf/regressiondoctor)：把"这次和上次比是不是真变差了"变成可自动判定的东西。
- 第五部 [fitdoctor](https://github.com/liu-perf/fitdoctor)：换方向问"这个数本来该是多少"。
- 第六部 telemetrydoctor：再换一次方向，问**"这个数我能拿去做什么运算"**。前五部都在看
  一次测量或两次测量之间；这一部看的是**一次长跑内部的时间轴**——秒级监控序列怎么切
  阶段、哪一列能求均值哪一列不能、哪一列乘以时长会错 69 倍。
- 第七部 [servedoctor](https://github.com/liu-perf/servedoctor)：把镜头转过来对着**测量
  装置本身**，问"这份压测报告测的是服务，还是压测器"。同一台服务器、同一个配置速率，
  闭环压测报出的 q99 比开环短 **16.5 倍**，而两者最大值只差 1.8 倍。它也和这一部撞过
  同一类错误：Little's Law 差一步被当成交叉验证，而在逐请求数据上它是恒等式。

第一部用**两套独立实现**交叉验证同一个 GEMM 结果（不是按架构比值——那张比值表是第五部自己的），第六部把同样的思路用在分段上：**同一份
文件切两次，方法必须互相独立，不一致就拒绝出结论。** 这条在实现时差点没做成——第一版
的第二种方法在代数上恒等于第一种，永远不可能不一致，是一条为了逼出分歧而写的测试把它
抓出来的。经过写在 [phases-and-thresholds.md](phases-and-thresholds.md) 里。
